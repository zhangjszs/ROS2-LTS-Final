## D-024 #95 根因口径订正：真实缺陷是「部分弧圆拟合失稳」，不是「以车为中心的虚假同心圆」（2026-10-26 Planner 自定，D-011 执行）

- 问题：#92 执行报告（并据此立项的 #95）把根因描述为「跨圆平均产生以车为中心、半径恒 9.125 m 的虚假同心圆，全路径距车身恒为 9.125 m」。D-011 要求：凡以「某处存在缺陷」为核心卖点的 Issue，进 `ready` 前 Planner 必须实测该断言。Planner 用**仓库真实实现**（`centerline_core.hpp` + `sensor_model_core.hpp`）+ **真实赛道 108 锥桶**做了一次性复现（未入仓库、未改仓库代码），结论是**方向对、定量错**。
- 实测：✅ `ClusterCones` 按 y=±0.3 割裂双圆成立；✅ `centerline_core.hpp:301-306` 跨圆平均致 cy 抵消到 ~0 成立（9/9 位姿）；✅ 回退中点法点序非单调成立（9/9 位姿，每次 x 回跳 2~4 次）；❌「距车身恒为 9.125 m、以车为圆心」**不成立**。真实机制更靠前——传感器量程 15 m、视场 120° ⇒ 每侧只见 15~17 个锥桶（只覆盖目标圆的一段**弧**），对部分弧做 Taubin 拟合剧烈漂移（实测半径 6.40 / 20.67 / 30.24 / 37.95 / 29.11 / 183.71 / 167.08 / 117.76 / 60.93 m），多数落在有效带 `[3, 25]` 外 ⇒ 圆法返空 ⇒ 线上长期走**中点法回退** ⇒ 点序非单调 ⇒ PP 窗口化最近点搜索锁到远处点 ⇒ `refusing goal` + 末端刹车。
- 决定：**订正 #95 的根因口径并按订正后的口径重写验收标准**（三处缺陷：部分弧当整圆拟合 / 左右圆被平均成单圆 / 点序非单调）；验收标准第 9 条要求 Executor 附 D-011 同款实测数字（拟合半径 / 平均圆 / 点序回跳数 / 横偏最小值），**不得只给结论**。
- 理由**：若沿用原口径立项，Executor 会去修「平均公式」而漏掉「部分弧拟合」这一真正的上游缺陷——那正是 D-011 要防的失败模式：断言错了，整轮返工。订正不影响 #92 的处置结论（仍是 needs-info）。
- 影响范围**：#95 正文与验收标准；PLAN §〇 与 §三的完成判据；D-011 的执行记录。**不触契约 1.10 红线**（纯算法层，不改公共 API / 契约 / 架构）。
- **可复用教训**：**别把「实测量级」当「机制」**。Executor 报告里最容易失真的就是把观测到的数字（9.125 m、10.03 m）直接写成机制，而真实机制可能在上游（部分弧拟合）。写 Issue 根因时，机制必须能被独立复现的数值支撑，且「复现不了」本身就是订正信号。
- **转正记录**：不适用（Planner 自定、低风险可回滚、纯事实订正）。

## D-013 `blocked` 标签是待验证断言，须分解为「资料 / 运行时 / 决策」三类（2026-10-19）

- 问题：#23 自 2026-10-05 挂 `blocked`，原因写「需 ROS1 环境」，7 轮规划里一直被当作整体外部阻塞对待（D-009 甚至规定"不再为找活而扫描"）。本轮实测发现：该断言把**两件不同的事**混在一起——「需要读到 ROS1 源码」与「需要运行 ROS1 运行时」。前者本机早已满足（`FSAC/2025` = `zhangjszs/ROS1-LTS-Final`，含 #23/#24 声明的基线 `1e7de39c` 且全部引用路径 `git cat-file -e` 可达；非浅克隆），后者确实缺失（`/opt/ros` 仅 `lyrical`、无 docker）。
- 决定：**`blocked` 不是终态标签，而是一条未经检验的前提。** 每轮治理（§4.1）对 P1/P2 的 `blocked` 单，Planner 必须把它分解为三类之一并写明证据：① **资料缺失**（协议文档、真实 bag、标定实值）→ 真外部，只能等；② **运行时/工具缺失**（需 ROS1 环境、需台架）→ 真外部，但**须实测确认本机没有**，不得凭印象；③ **决策缺失**（选哪个赛制、后端取舍）→ 属 §6.1「必须问用户」，应转 `needs-info` 而非长期 `blocked`。三种可执行性完全不同，混在一起会让一个可拆出的子任务跟着不可拆的部分一起挂着。
- 已按此处理：#23 的机械对照部分拆出 **#77**（P1 `ready-for-agent`），#23 本体转 `needs-info`，#24 的阻塞措辞精确化为「需 ROS1 运行时」。**剩余 #15/#16/#17/#18/#19/#37 待后续轮次逐个按此口径复查**（每轮查 1–2 个即可，不必一次扫完）。
- 与 D-011 的关系：D-011 管 `ready` 侧（立项时的技术断言须实测），本条管 `blocked` 侧（阻塞时的前提须实测）——同一失败模式的两个方向。二者共同的根因是 7 天零执行导致**没有任何反馈渠道能暴露未经检验的断言**：既没人验证 #62 的 UB，也没人验证 #23 的阻塞。
- 附带事实更正（跨仓有效）：**`FSAC/2024`（`HUAT-FSAC/ROS1_FIN_VERSION`）不是 #23/#24 的 ROS1 对照基线**——该仓 `src/autodrive_msgs/msg/` 无 `HUAT_PathLimits.msg`、`src/` 下无 `vehicle_interface_*` 包；#23/#24 链接的一直是 `zhangjszs/ROS1-LTS-Final`（= `FSAC/2025`）。姊妹仓 2024 的 D-001=C 决策所依据的"本仓即那个 ROS1 环境"前提与本条冲突，已在该侧按其 §6.3 重新向用户确认一次。
- 影响范围：每日循环第 4 步（队列治理）的检查清单；D-009 维持模式**不构成例外**——"不为找活而扫描"不等于"不验证已有阻塞"。
- 转正记录：不适用（本轮自定纪律，非用户决策）。

## D-014 首个端到端闭环赛制 = 直线加速（2026-10-20 用户亲选）

- 问题：#23 悬置的决策缺失项之一——优先闭环哪个赛制（直线加速 / 八字绕环 / 高速循迹）。该选择决定 S2 阶段的范围、定位精度要求与仿真评测口径。
- 决定：**首个端到端闭环赛制选定为直线加速。** 判据以「跨越 x=75 m 终点线 + 在 x≤100 m 的 25 m 缓冲区内停车」为准；八字绕环与高速循迹暂不纳入当前里程碑，待 S2a 闭环后再评估。
- 理由：① 现成资产最厚——`track_benchmark` 已有 `GenerateAcceleration`（终点 x=75、中心线延伸至 x=100）、`acceleration.acceleration-75m.v1.json` 基线、CI 回归门；② 定位需求最低——纯 INS 站心坐标即可（与 D-015 相互支撑）；③ 控制链最短，是验证「感知→规划→控制→仿真」全链路的最优最小切口。
- 影响范围：S2a 里程碑与 #80（直线加速事件判定）；后续规划不得在 S1/S2a 未闭环前把八字/高速的实现任务拉进 `ready`；赛道几何与判据改动须同步 `benchmarks/baseline/` 与 KPI 口径。

## D-015 定位后端：暂缓 mapper / ESKF / 因子图，纯 INS 基线（2026-10-20 用户亲选）
